# RD68884 patches

Against **RD68884 0595f34** ("RD68885: works in the Macintosh IIsi; docs say
so"), the commit checked out under `Inputs/RD68884`.

`scripts/patch_rd68884.sh` makes the patched copy, `~/LITEX-68K/RD68884`
(disposable): a clone of that commit, these patches applied with `git am`, and
the generated microcode (`rtl/gen/`) regenerated by RD68884's own `make ucode`
and committed. `scripts/sync_pythondata.sh` takes the FPU from that copy
whenever this directory has patches, and the pythondata package records them
(`fpu_patches`).

The patches carry only sources (`tools/`). RD68884 commits its generated
files, but a regenerated ROM moves every microcode word after a change, which
would make a one-line fix a 700 KB patch. Upstream, `make ucode` regenerates
them.

To change a patch: edit `~/LITEX-68K/RD68884`, run RD68884's `make check`, and
`git format-patch -o <this directory> 0595f34.. -- tools` (without the
regeneration commit).

## 0001-FSAVE-while-a-released-instruction-waits-for-its-rel.patch

**What:** a register-to-register instruction (`src_rr` in
`tools/ucode/arith_ucode.py`) and FMOVECR post their release (null, CA=0),
then waited for the main processor to read it, looking at nothing else. A save
request there was never answered, so FSAVE got come-again forever.

The sequence that leads there:

1. An instruction is still computing (FSIN, say), and the next one is latched
   behind it. The CPU polls the response CIR and gets null CA=1 IA=1.
2. The CPU takes an interrupt during those polls, with a mid-instruction frame,
   and the handler saves the FPU, as an operating system's context switch does.
3. The computation ends. The microcode takes the latched instruction, posts
   its release, and waits for the CPU to read it, which the CPU will only do
   after the handler's RTE.

Both paths now `CALL wait_first`, as the memory-source and FMOVE-out paths
already did. A save request there saves an idle frame with the instruction
pending, and FRESTORE starts it again. The register file's output is taken one
clock later than before.

The patch adds the ISS test
`IssOnly.test_interrupt_while_latched_behind_computation`
(`tools/iss/tests/test_vs_model.py`). It runs the sequence with FMUL and with
FMOVECR as the latched instruction, and compares the registers with a run that
has no interrupt. Both cases hung before the fix. With the fix, RD68884's
`make check` passes, and the same scenario on the MC68882 build (RD68885)
saves its idle frame. `make cycles` was not run: it needs RD68021, which is
not here. The register-to-register path is one clock longer, so its frozen
counts will move.

**Why:** Linux on RD68031 with RD68884 froze as soon as two processes using
the FPU preempted each other, on the board and in litex_sim. The freeze was
the scheduler's FSAVE (`doc/l7-linux.md`). This project's
`sim/litex/fpswitch/` reproduces it bare-metal: two FPU tasks switched by a
timer interrupt, the FPU saved and restored as Linux's `resume` does. RD68884's
own system test, SunOS on RD68021, never took an interrupt at that point.

**Upstream:** not sent.
